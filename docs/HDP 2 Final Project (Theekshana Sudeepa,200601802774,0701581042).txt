Abstract (<=250 words)
LexoraFix is an Android mobile commerce and home-services marketplace application built to combine product purchasing with service booking in a single, real-time user experience. The system consists of two client modules: a customer application and an admin/worker application. Customers register and authenticate using Firebase Authentication (email/password and Google sign-in), optionally enable biometric quick login, browse products by category with live stock information, and manage wishlist and cart items. Checkout is implemented using the PayHere payment gateway; after successful payment the app creates an order and synchronizes it to Cloud Firestore using a dual-write pattern. Product inventory is decremented transactionally to reduce overselling. Customers can book services by selecting date/time, writing notes, capturing GPS location (or selecting a map location), and monitoring booking status in real time. Communication is supported with Firestore-backed chat and event-driven notifications delivered through Firebase Cloud Messaging and Cloud Functions (Firestore triggers).
Administrators manage catalogue data (products, categories, service centers), monitor operational analytics, and update order and booking statuses. Workers accept jobs using Firestore transactions to avoid concurrent claims, progress work through defined status transitions, and chat with customers. The overall solution enforces role-based access control using Firestore Security Rules and includes a maintenance-mode mechanism for controlled system availability.

1. Introduction
1.1 Motivation
Home improvement and maintenance tasks often require both purchasing products (tools, accessories, replacement parts) and arranging professional services (installation, repair, maintenance). In many real-world scenarios these steps are handled through separate systems, leading to a fragmented user journey. Users can experience duplicated browsing steps, inconsistent stock visibility, delayed updates on progress, and limited communication between customers and service providers.

LexoraFix is motivated by the need for a unified mobile platform that supports:
- Product discovery and purchasing
- Service booking with scheduling and location support
- Real-time tracking, notifications, and chat coordination
- Administrative control over catalogue and operational workflow

1.2 Problem Statement
The project addresses the following issues:
- Lack of a single interface for both commerce and service booking.
- Inventory and stock changes that are not reflected quickly enough, causing invalid purchases.
- Unreliable status communication between admins/workers and customers.
- Difficulty for customers to coordinate with assigned workers after a booking is accepted.
- Security challenges: ensuring that customers and workers can only access permitted data, while admins can manage the full system.

1.3 Objectives
The objectives of LexoraFix are:
- Implement a customer app that supports registration/login, product browsing with filtering, wishlist and cart management, PayHere checkout, order tracking, and service booking.
- Implement an admin/worker app that supports RBAC-protected access, operational dashboards, catalogue CRUD, order/booking status management, and transactional worker job acceptance.
- Use Firebase backend technologies to provide real-time updates via snapshot listeners and event-driven notifications via Cloud Functions and FCM.
- Enforce security using Firestore Security Rules and maintain correctness of workflow transitions using transactions and dual-write synchronization.

1.4 Scope and Report Overview
This report covers the system design and implementation of LexoraFix across:
- Data modeling and Firestore schema design
- End-to-end user flows (orders, bookings, chat, notifications)
- Implementation details at code-module level (activities, adapters, helpers, services)
- Security enforcement and workflow guards
- Evaluation approach and limitations

2. Background
2.1 M-Commerce and Service Marketplaces
Mobile commerce enables shopping from mobile devices, usually focusing on catalogue, cart, and checkout. A service marketplace adds coordination complexity because service fulfillment is a multi-step workflow. Typical marketplace requirements include:
- Asynchronous events (job accepted, work started, completed)
- Status-driven UI updates
- Assignment and conflict prevention
- Messaging and notifications for coordination

LexoraFix models service fulfillment as a state machine driven by Firestore document fields and synchronized across roles.

2.2 Technologies Used
LexoraFix uses:
- Firebase Authentication for identity (customer/admin/worker).
- Cloud Firestore for the primary database with real-time listeners.
- Firebase Storage for product/category/user images.
- Firebase Cloud Messaging (FCM) for push notifications.
- Firebase Cloud Functions (Firestore triggers) to react to document changes and send notifications.
- Google Maps SDK for location visualization and map-based selection.
- PayHere Android SDK for payments in Sri Lanka.
- JavaMail-based email utilities for transactional communication.

2.3 Security Model (RBAC)
Security is enforced primarily through Firestore Security Rules. The rules determine access using role information stored under `users/{uid}`. Helper functions such as `isAdmin()` and `isWorker()` restrict reads/writes to:
- admin-controlled collections and system settings
- user-owned documents (orders/bookings)
- worker-controlled booking status transitions under allowed conditions

Additionally, client-side navigation checks are used for user experience (e.g., redirecting based on role and email verification), but enforcement remains server-side through rules and transactions.

3.4 Data Model and Firestore Schema
Primary top-level collections:
- `users`: user profiles (role, status, tokens).
- `products`: product definitions (stock, variants, images).
- `categories`: category metadata and images.
- `service_centers`: service locations with coordinates and contact info.
- `orders`: order documents for admin visibility and tracking.
- `bookings`: service booking documents for admin and worker visibility.
- `chats`: chat headers with subcollection `chats/{chatId}/messages`.

User-specific subcollections:
- `users/{uid}/orders`: customer view for order tracking.
- `users/{uid}/bookings`: customer view for booking status tracking.
- `users/{uid}/notifications`: in-app notifications displayed by `NotificationFragment`.

Product reviews:
- `products/{productId}/reviews`: review objects for moderation and display.

4. Implementation
4.1 Customer App Implementation
Authentication and roles:
- `LoginActivity` performs sign-in (email/password, Google) and checks role and email verification status from Firestore. It navigates users to the correct module based on role.
- Biometric login is supported by enabling biometric prompt setup and verifying biometric-enabled state for faster re-authentication.

Navigation, maintenance mode, and UI:
- `MainActivity` hosts bottom navigation and loads fragments for Home, Categories, Cart, Services, and Profile.
- `MainActivity` listens to the `maintenance_mode` setting in Firestore and redirects users to `MaintenanceActivity` when required.
- A shake gesture is implemented to quickly reach the services workflow.

Catalogue browsing:
- `HomeFragment` loads categories and featured products.
- Product lists support live search and filtering; filter UI is implemented using fragments and chips/range sliders.
- `ProductDetailActivity` listens to product changes to keep stock information up to date.

Checkout and payments:
- `CheckoutActivity` validates stock before payment.
- Delivery address input includes province/district selections and delivery fee logic.
- PayHere SDK is initialized and the payment request is launched. On success, `placeOrderAfterPayment` stores order details and triggers local and Firestore updates.

Orders and tracking:
- Order status changes are delivered to the user using `OrderStatusService` which listens to Firestore status updates.
- `OrderTrackingActivity` shows a timeline of order states based on the order `status` field.

Service booking:
- `BookServiceActivity` gathers booking date/time and notes.
- Location is captured by GPS (with reverse geocoding) or by `LocationPickerActivity`.
- Booking is synchronized to Firestore (top-level and user subcollection).

Chat:
- `ChatActivity` uses chat headers and message subcollections under `chats/{chatId}/messages`.
- Chat is enabled for active bookings and disabled once the booking is completed.

4.2 Admin/Worker App Implementation
Login and maintenance mode:
- `AdminLoginActivity` authenticates admins and workers, verifies roles using Firestore, and routes to the correct dashboards.

Admin dashboard and analytics:
- `AdminDashboardActivity` uses listeners to compute operational metrics (e.g., number of users/orders/bookings/products) and displays them in the UI.

Catalogue management:
- `ManageProductsActivity` allows adding/editing/deleting products and also supports reviewing product reviews.
- Category and service center management is handled by admin screens with consistent Firestore CRUD.

Order management:
- `ManageOrdersActivity` lists orders and allows status updates via UI dialogs.
- Status update logic ensures updates are mirrored to both top-level orders and customer subcollection views.

Booking and worker workflows:
- `ManageBookingsActivity` enables booking status updates and notifies customers through status change mechanisms.
- Workers accept jobs using `WorkerBookingAdapter` and Firestore transactions to prevent double assignment.
- Workers update their assigned job status progression and can chat with customers.

4.3 Cloud Functions and Notification Pipeline
The backend uses Cloud Functions (Firestore triggers) in `functions/index.js` to implement event-driven notifications:
- New booking created: notify approved workers via FCM.
- Booking status changes: notify the customer and write an in-app notification document to `users/{uid}/notifications`.
- New chat message: send push to the other participant and log in-app notifications when applicable.
- New order created: notify admins.
- Order status changes: notify the customer and log in-app notification documents.

This architecture ensures that notifications are still delivered accurately even when users are not actively using the relevant screens.

4.4 Payments, Email, and Media Storage
Payments:
- PayHere SDK is integrated through `CheckoutActivity`. Merchant identifiers are stored in `BuildConfig`.

Email:
- `EmailHelper` uses JavaMail to send transactional emails for order confirmations and status updates.

Media storage:
- `StorageHelper` uploads images to Firebase Storage and updates Firestore documents with download URLs.

4.5 Real-Time Synchronization and Local Persistence
Local cart persistence:
- SQLite persistence is implemented via `DatabaseHelper` for cart-related data.

Cloud synchronization:
- Orders and bookings use dual-write patterns to support both admin visibility and customer-specific listeners.
- Real-time updates are delivered through snapshot listeners, which keep the UI responsive with minimal delay.

5. Results and Evaluation
5.1 Functional Verification (End-to-End)
Functional verification was performed by validating the main user journeys through the app modules:
- Customer authentication flows (email/password, Google sign-in, biometric quick login).
- Product catalogue browsing including category selection, search/filter, and variant selection.
- Wishlist toggling and cart updates with stock constraints.
- PayHere checkout success path and subsequent order creation synchronization.

- Service booking creation with GPS/map location and status tracking.

5.2 Security Verification (Rules and Workflow Guards)
Security verification was evaluated using:
- Firestore Security Rules inspection and RBAC logic review (admin vs worker vs customer).
- Transaction-based workflow guards (worker booking acceptance) to reduce race conditions.
- Controlled actions through callable functions (e.g., admin-driven deletion).

5.3 Limitations
Important limitations include:
- Some legacy local persistence patterns may require refinement for a fully offline-first experience.
- Review verification relies on stored purchase history; additional business rules can be added for edge cases.
- Notification reliability depends on correct token management for FCM; token refresh/update logic should be monitored.

6. Future Work
Future improvements for a next iteration:
- Stronger payment verification using backend confirmation (webhooks) to reduce reliance on client SDK outcomes.
- Full offline queueing for cart and checkout with conflict resolution on reconnect.
- Enhanced stock model for variant stock granularity and more robust stock transition invariants.
- Improved chat UX: read receipts, message attachments, and better deep linking.
- Map improvements: caching, marker clustering, and smarter distance calculation performance.

7. Conclusions
LexoraFix provides an end-to-end mobile commerce and home-services marketplace solution. The customer app supports product browsing, wishlist and cart management, PayHere-based checkout, real-time order tracking, and service booking with location support and chat. The admin/worker app supports role-based operational control, catalogue CRUD, status transitions for orders and bookings, and transactional worker job acceptance. The system uses Firebase Authentication, Cloud Firestore, Firebase Storage, Cloud Functions, and FCM to deliver real-time data synchronization and reliable event-driven notifications. Security is enforced through Firestore Security Rules with RBAC, and workflow correctness is improved using Firestore transactions for critical assignments.

8. Reflection on Learning
This project aligns with Argyris' double-loop learning concept. The development process influenced not only technical skills but also underlying assumptions:
- Early assumption that UI checks alone are enough for access control was corrected after security review; server-side RBAC rules became a primary design constraint.
- Early assumption that local-only data patterns can keep the experience consistent was corrected by adopting dual-write patterns and snapshot listeners for real-time updates across roles.
- Early assumption that job assignment can be handled with simple updates was corrected by adding transactional acceptance to prevent concurrency issues between workers.
- Early assumption that notifications can be handled purely on-device was corrected by combining push notifications (FCM) with Cloud Functions and in-app notification document logging.
